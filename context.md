# Роадмап: Transito Lite на Go → перший оффер у Мюнхені

**Вихідна точка:** база JS/TS/React (з 2020, потім була перерва), простий CRUD на Express. Принципи бекенду розумію, але треба повернути практику.
**Час:** 1–2 год/день (~10 год/тиждень).
**Ціль:** Junior/Mid Fullstack (React + Go) у Мюнхені.
**Проєкт:** Transito Lite. Це новий продукт, написаний з нуля власноруч. Старий Transito слугує тільки довідником по домену.

---

## Продукт в одному реченні

Перевізник отримує **посилання, за яким пасажири бронюють самі, навіть коли він спить**.

**Назва:** поки що залишаємо Transito. «Lite» — тільки робоча назва проєкту.
**Дизайн:** макети 4 екранів (рейси, бронювання, «заявку надіслано», Telegram перевізника): https://claude.ai/artifact/PyzBtMbdWGDmrAwUpfS4pw

### Функціонал MVP

**Перевізник** (тільки Telegram):

- реєструється в Telegram-боті й отримує своє посилання
- додає рейси або шаблон розкладу
- отримує нові броні з кнопками «Підтвердити / Відхилити»
- зменшує кількість місць або закриває рейс
- бачить список пасажирів на рейс
- отримує тижневий звіт
  **Пасажир** (сторінка без реєстрації):
- відкриває посилання й бачить найближчі рейси
- обирає рейс і вводить ім'я, телефон, кількість місць
- бачить статус броні за посиланням
- може подзвонити перевізнику
- може скасувати бронь

### Прийняті рішення

- Ціна рейсу показується на сторінці
- Оплата водію при посадці (онлайн-оплати немає)
- Скасування рейсу: всі активні броні стають cancelled, пасажирів повідомляють
- Пасажир бачить статус на сторінці, перевізник за потреби телефонує
- Максимум 5 місць в одній броні
- Дизайн: темно-синій (#14213D) + жовтий акцент (#FFC93C), шрифти Unbounded (заголовки) та Inter (текст), mobile-first

### Свідомо НЕ робимо в MVP

Оплата, CRM, акаунти пасажирів, SMS, відгуки, мапа, кілька мов.

### Відкриті питання

- Захист від фейкових броней: ліміт на номер та IP + підтвердження перевізником
- **Поговорити з двома перевізниками, які пробували старий Transito: чому пішли?**

---

## Правила навчання

1. **Код пишу я сам.** Claude пояснює, ставить завдання і робить рев'ю, але готових рішень не генерує.
2. Кожна тема Go з'являється тоді, коли вона потрібна продукту.
3. Кожен етап закінчується робочим результатом і комітом.
4. Пишу тести з першого етапу.
5. Щодня хоча б маленький коміт.

## Етап 0. Розгін (тиждень 1)

- [x] Продумати функціонал, назву, дизайн

- [ ] Перший репозиторій `transito-lite`, `go mod init`, «hello world», коміт

## Етап 1. Домен без бази і HTTP (тиждень 2–3)

Go: structs, methods, slices, maps, errors, interfaces, пакети, тести

- [ ] Типи `Trip`, `Booking`, статуси як константи
- [ ] Логіка: `Book(trip, seats)`, `Confirm`, `Reject` і `Cancel` (повертають місця), валідація телефону, ліміт 1–5 місць
- [ ] Свої помилки: `ErrNotEnoughSeats`, `ErrTripDeparted`, `ErrTooManySeats`
- [ ] Table-driven тести на всю логіку
- **Результат:** пакет `booking` зі 100% зрозумілою логікою і тестами

## Етап 2. HTTP API in-memory (тиждень 4–5)

Go: `net/http`, `ServeMux` (Go 1.22+ патерни), JSON, middleware, `httptest`

- [ ] `GET /c/{slug}/trips`: найближчі рейси
- [ ] `POST /c/{slug}/trips/{id}/bookings`: бронь
- [ ] `GET /b/{token}`: статус броні для пасажира
- [ ] `POST /b/{token}/cancel`: скасування броні пасажиром
- [ ] Middleware: логування (`slog`), recover, request ID
- [ ] Тести хендлерів через `httptest`
- **Результат:** API, яке можна смикати через curl/Postman

## Етап 3. PostgreSQL і конкурентність (тиждень 6–8)

Go: `pgx`, `sqlc`, міграції (`goose`), транзакції, goroutines у тестах

- [ ] Схема БД і міграції, docker-compose з Postgres
- [ ] Repository-шар, структура handler → service → repository
- [ ] **Гонка за останнє місце:** транзакція + `SELECT … FOR UPDATE` або атомарний `UPDATE … WHERE seats_left >= $1`
- [ ] Тест: 50 goroutines одночасно бронюють 8 місць, рівно 8 успішних
- [ ] Інтеграційні тести з testcontainers
- **Результат:** надійне ядро бронювання. Це головна історія для співбесіди.

## Етап 4. Telegram-бот для перевізника (тиждень 9–11)

Go: HTTP-клієнт, webhooks, outbox pattern, worker pool, `context`, graceful shutdown

- [ ] Реєстрація перевізника в боті: назва, телефон → видати посилання; прив'язка chat_id
- [ ] Нова бронь → запис в `outbox` у тій самій транзакції
- [ ] Воркер: читає outbox (`FOR UPDATE SKIP LOCKED`), шле повідомлення з inline-кнопками, робить повтори з backoff
- [ ] `callback_query`: Підтвердити / Відхилити → оновити бронь, відредагувати повідомлення
- [ ] Повідомлення перевізнику, коли пасажир скасував бронь
- [ ] Команди: «−N місць», «рейс заповнений», список пасажирів на рейс
- [ ] Graceful shutdown по SIGTERM
- **Результат:** перевізник повністю керує бронями з Telegram

## Етап 5. Розклад і звіти (тиждень 12–13)

Go: `time`, часові пояси, планувальник, тикери

- [ ] Додавання разового рейсу і шаблону розкладу через бота (покроковий діалог)
- [ ] Шаблони розкладу → автоматичне створення рейсів на 2–4 тижні вперед
- [ ] **Тижневий звіт:** кількість броней, скільки з них вночі (22:00–7:00 за часовим поясом перевізника)
- [ ] Автозакриття рейсів, що вже виїхали
- **Результат:** продукт працює сам, без ручної роботи

## Етап 6. Сторінка бронювання (тиждень 14–16)

React + TS + Vite + TanStack Query, mobile-first, за макетами

- [ ] Сторінка `/c/{slug}`: шапка перевізника + «Подзвонити», список рейсів (ціна, вільні місця, «немає місць»)
- [ ] Форма бронювання: ім'я, телефон, лічильник місць (1–5), сума, одна кнопка
- [ ] Сторінка статусу броні `/b/{token}`: статус, деталі, «Подзвонити», «Скасувати»
- [ ] Rate limiting на бекенді (на номер та IP)
- [ ] CORS або роздача статики з Go
- [ ] Перевірка на реальному телефоні, швидкість, доступність
- **Результат:** пасажир бронює за 20 секунд
